# Протокол проверки FoodExpress

Проверено 10 ноября 2026 на PostgreSQL 15.19 (Linux aarch64), в изолированном контейнере с лимитами 2 CPU и 1.5 GiB RAM. TimeZone — Europe/Moscow, work_mem — 4 MB. Итоговые SQL после разбиения по тикетам создают новую схему без ошибок.

**119 утверждений прошли под `inspector` в исходной БД; те же 119 прошли после восстановления свежего custom-архива в другую пустую БД.** В каждом прогоне: 70 основных + 39 регрессионных + 10 граничных. Это утверждения, а не 119 независимых бизнес-требований. Подключения проверялись по TCP с `scram-sha-256`; неверный пароль отклонён. Повторный `grants.sql` сохранил существующий пароль.

| БД | checks.sql | boundary_checks.sql, включая regression | Итог |
|---|---:|---:|---|
| foodexpress_final_v3 | 70 OK, 0.617 с | 49 OK, 0.715 с | exit 0 |

Три ожидаемые ошибки COMMIT в каждом втором сценарии подтверждены проверками SQLSTATE и отката. Без параметра имени БД или с чужим именем проверочные скрипты прекращают работу до изменения данных (проверено четыре отказа, exit 3).

## Безопасная среда и запуск

Проверки удаляют данные проекта. Запускать только в отдельной пустой тестовой БД после установки текущей схемы и выдачи прав `inspector`. Все сценарии требуют явного `-v foodexpress_test_database=<имя тестовой БД>` и сверяют его с `current_database()`, а пользователя — с `inspector` до очистки. Не передавать имя рабочей БД.

Два отдельных подключения `psql -X -v ON_ERROR_STOP=1`:

1. `-v foodexpress_test_database=<имя> -f db/checks.sql` — генератор, метаданные, ограничения, процедуры, очистка.
2. `-v foodexpress_test_database=<имя> -f db/boundary_checks.sql` — сначала автоматически подключает `regression_checks.sql`, затем проверяет пороги выплат и календарные границы. Отдельный повторный запуск regression для полного прогона не нужен.

`regression_checks.sql` также можно запускать отдельно в новом подключении. Его вспомогательные функции находятся только в `pg_temp`, не входят в схему и дамп. Данные создаются вручную, без `insert_test_data`, чтобы ошибка генератора не могла одновременно создать неверную модель ожидаемого результата.

В регрессионном сценарии три сообщения PostgreSQL об ошибке COMMIT ожидаемы. На коротком участке отключается `ON_ERROR_STOP`, сразу сохраняется SQLSTATE, затем включается обратно. Успех определяется последующими утверждениями о коде `23514` и полном откате, а не отсутствием текста ERROR в журнале.

Сохранение существующего пароля проверялось сравнением в серверной временной таблице без вывода пароля или его хеша.

## Конкурирующие транзакции

В отдельной `foodexpress_integrity` воспроизведены и исправлены два случая взаимоблокировки: разные позиции одного заказа; позиции разных заказов с одним блюдом и последующие отзывы. После смены режима блокировок обе транзакции фиксируются, итоговый рейтинг равен AVG отзывов.

Гонка смены ресторана блюда с добавлением позиции проверена отдельно: READ COMMITTED отклоняет несогласованное действие с `23514`; REPEATABLE READ теперь явно отклоняет смену принадлежности с `0A000`; при двух SERIALIZABLE одна транзакция получает `40001`. После каждого сценария неверных связей нет. Это проверка конкретных сценариев, а не доказательство отсутствия всех возможных взаимоблокировок.

## Отчёты на большом наборе

`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` выполнялся на 50 000 заказах и 10 000 ресторанах после ANALYZE. Один прогрев и три измерения каждого варианта, одна и та же выборка. Повторный замер выполнен после окончания параллельного нагрузочного QA.

| Выбор лидеров | Медиана исполнения |
|---|---:|
| DISTINCT ON, текущая реализация | 153.819 мс |
| row_number | 165.871 мс |
| предварительный MAX + выбор случайного среди равных | 188.181 мс |

Оставлен DISTINCT ON: он проще альтернативы с дополнительными агрегациями и на этом наборе не уступил ей. Эти числа относятся к данной среде и распределению данных. В исходной таблице заказов один проход для CTE доставленных заказов; дальнейшие агрегации используют его. Сортировка может писать во временные файлы при стандартном work_mem, это отражено в сохранённых планах.

## Генерация большого набора

На итоговом генераторе под inspector проверен `insert_test_data(10000)`: 50 000 заказов, 150 196 позиций, по 50 000 отзывов и оплат, 60 000 строк истории выплат. Всего в 12 таблицах — **550 196 строк**. Очистка предыдущего набора, генерация и COMMIT вместе заняли **45.127 секунды**; в диагностическом прогоне добавлялись только сообщения времени этапов, затем процедура восстановлена из SQL проекта. Обычные планы PostgreSQL сохранены, принудительное перепланирование не используется.

Независимые сверки не нашли расхождений суммы позиций/заказа, числа успешных оплат, рейтингов блюд/ресторанов и выплат. `get_statistic()` вернул 10 000 строк, денежный отчёт — шесть месяцев. На этом проверку объёма остановили; миллион заказов не проверялся.

Позиции, отзывы и оплаты вставляются пакетами через параллельный unnest. Описание отзыва сначала вычисляется в скалярную переменную, затем добавляется в массив. Подзапрос непосредственно внутри array_append вызывал копирование растущего массива: микротест на 5000 строках занял 1.931 с вместо 0.049 с при разделении операций. Полный промежуточный вариант занимал 291.326 с, итоговый — 45.127 с в той же ограниченной среде; это измерение данного набора, а не гарантия времени на любой машине.
