# Ограничения FoodExpress

Решение использует схему `lukovkin_food` и PostgreSQL 15 или новее. Все 12 сущностей задания представлены таблицами. Для заказа выбрано имя `order_core`, для попытки оплаты используется `payment_core` (BR-13.1/13.2). Представления `"order"` и `payment` возвращают поля из задания, в том числе вычисляемые суммы.

## Типы и диапазоны

| Тип | Значения | Правило |
|---|---|---|
| restaurant_status | активен, неактивен | BR-4.3 |
| product_status | доступно, нет_в_наличии, архив | BR-5.5 |
| courier_status | свободен, занят, на_доставке, уволен | BR-6.2 |
| order_status | создан, готовится, в_доставке, доставлен, отменён | BR-7.7 |
| order_pay_status | ожидает, оплачен, ошибка | BR-7.9 |
| payment_status | успех, ошибка, в_обработке | BR-8.2 |
| payment_type | карта, наличные, безнал | BR-8.2 |
| review_entity_type | блюдо, ресторан, заказ | BR-9.1 |

Идентификаторы имеют тип UUID, включая внешний идентификатор финансовой транзакции. DEFAULT идентификаторов сущностей вызывает `exts.uuid_generate_v4()` (BR-11.1). Схему `exts` и расширение заранее подготавливает администратор; скрипты решения их не меняют (BR-13.3).

Для названий выбраны `varchar(80..120)`, для частей ФИО используется `varchar(50)`, для частей адреса предусмотрены `varchar(12)` и `varchar(100)`. Телефон состоит из 11 цифр без оформления, пароль хранится в виде 32 шестнадцатеричных символов.

Реквизиты `inn`, `ogrn`, `settlement_account` записываются строками, чтобы сохранить ведущие нули. Проверяется длина: 10/12, 13/15 и 20 цифр соответственно. Контрольные суммы и действительность реквизитов не проверяются. Это выбранные технические форматы по BR-11.6.

Денежные поля имеют два знака после запятой, количество имеет три. Верхние границы ниже определяются типами хранения; отдельных бизнес-ограничений на такие максимумы в задании нет. Для итогов отчётов используется `numeric` без ограничения точности.

| Поля | Тип | Верхняя граница хранения | Обоснование |
|---|---|---|---|
| `product.price`, `order_structure.unit_price` | `numeric(7,2)` | 99 999.99 | Цена одной позиции доставки |
| `order_structure.quantity` | `numeric(6,3)` | 999.999 | Дробное количество; до тысячи единиц одного блюда в заказе |
| `order.order_amount`, `order.commission` | `numeric(8,2)` | 999 999.99 | Сумма отдельного заказа до комиссии и сама комиссия |
| `order.total_amount`, `payment.amount` | `numeric(9,2)` | 9 999 999.99 | Запас разряда для 10% комиссии поверх максимальной суммы блюд |
| `courier_pay.amount` | `numeric(9,2)` | 9 999 999.99 | Месячная выплата одному курьеру |
| Рейтинги | `numeric(3,2)` | Ограничены CHECK | Дробная оценка и округлённое среднее |
| Коэффициенты | `numeric(2,1)` | Ограничены CHECK 0.1..0.5 | Точность по BR-6.4/BR-10.2 |

Если сумма позиций не помещается в тип суммы заказа, запись отклоняется. Генератор формирует данные в этих пределах. Для увеличения диапазонов потребуется изменить типы.

## Нормализация

Адреса клиентов и позиции заказов вынесены в таблицы связей. Их атрибуты зависят от полного составного ключа. Названия ресторанов и категорий, логины клиентов хранятся в своих таблицах.

Вместо `courier.fio` используются фамилия, имя и необязательное отчество. Поле `restaurant.company_details` разделено на ИНН, ОГРН/ОГРНИП и расчётный счёт. Такое уточнение модели допускают `docs/erd.md` и BR-13.2. Реквизиты могут совпадать у нескольких ресторанов, поэтому уникальность ИНН и счёта не задана. Отдельного справочника юридических лиц нет; история реквизитов не ведётся согласно BR-4.5.

Автор отзыва определяется по связи `review.order_id → order.client_id → client.client_id`. Представление `review_with_client` возвращает все поля отзыва и client_id через JOIN. Оно предназначено для чтения. При записи в review достаточно заказа; выбор доступных пользователю заказов проверяет приложение. Если владелец заказа меняется, представление показывает нового владельца. Отдельной истории авторства в задании нет.

Так из таблицы отзывов исключена зависимость `review_id → order_id → client_id`. Ещё две зависимости устранены разделением таблиц и представлений:

- `order_amount → commission, total_amount`: сумма блюд хранится в `order_core`, комиссия и итог вычисляются в `"order"`.
- `payment_id → order_id → amount`: в `payment_core` хранятся сведения о попытке, а `payment` получает её сумму из заказа. Все попытки одного заказа показывают один итог.

Таблицы соответствуют 3НФ относительно зависимостей, заданных бизнес-правилами:

| Таблицы ядра | Ключи и зависимости |
|---|---|
| `client` | `client_id`, уникальные login и phone_number определяют остальные атрибуты |
| `address` | Альтернативные ключи: `address_id` и физический адрес с `NULLS NOT DISTINCT` |
| `client_address` | Только составной ключ `(client_id, address_id)` |
| `restaurant` | `restaurant_id` и уникальный `address_id` определяют остальные атрибуты; зависимости между реквизитами ТЗ не задаёт |
| `courier` | Атрибуты определяются `courier_id`; статус не определяет конкретную дату увольнения |
| `courier_pay` | Сумма и применённая ставка зависят от полного ключа `(year, month, courier_id)` |
| `product_category` | Название определяется `product_category_id` |
| `product` | Атрибуты определяются `product_id`; имя категории и сведения ресторана не дублируются |
| `order_core` | Атрибуты определяются `order_id`; производных денежных столбцов нет |
| `order_structure` | Количество и историческая цена зависят от полного ключа `(order_id, product_id)` |
| `payment_core` | Факты попытки зависят от `payment_id`; итог заказа не хранится |
| `review` | Ключи: `review_id`, `(order_id, entity_type, entity_id)` и `(order_id, product_id, restaurant_id)` с `NULLS NOT DISTINCT` |

Для полиморфной ссылки в review хранятся `entity_type` и `entity_id`. Поля `product_id` и `restaurant_id` вычисляются из них. У отзыва на блюдо заполнен product_id, у отзыва на ресторан заполнен restaurant_id, у отзыва на заказ оба поля равны NULL. Составные FK проверяют купленное блюдо и ресторан заказа; CHECK проверяет ссылку на сам заказ.

Ограничение `review_target_unique` закрепляет альтернативный ключ из order_id и двух проекций с семантикой `NULLS NOT DISTINCT`. Он минимален: без restaurant_id совпадут отзывы на заказ и ресторан, без product_id совпадут отзывы на заказ и блюдо, без order_id совпадут отзывы из разных заказов. Обе проекции входят в этот ключ. Поэтому зависимость `(entity_type, entity_id) → product_id, restaurant_id` допустима в 3НФ: атрибуты справа ключевые. Обычного UNIQUE здесь было бы недостаточно из-за повторных NULL. Это ограничение выражает существующее правило об одном отзыве на объект в заказе.

Рейтинги, сумма блюд и статус оплаты рассчитываются по строкам других таблиц. Внутри своих таблиц они не образуют транзитивных зависимостей между неключевыми атрибутами. Согласованность проверяют триггеры. Производные зависимости в представлениях допустимы: требование 3НФ относится к хранимым таблицам.

## Суммы и операции с заказом

Цена `order_structure.unit_price` фиксируется при оформлении. Она зависит от полного ключа `(order_id, product_id)`: в разных заказах одно блюдо может иметь разную цену. DEFAULT для неё нет, значение передаёт приложение или генератор. Изменение `product.price` не меняет уже оформленные заказы.

На COMMIT проверяется `order_amount = round(SUM(quantity * unit_price), 2)`. Сначала суммируются позиции, затем округляется результат. Представление заказа вычисляет `commission = round(order_amount * 0.10, 2)` и `total_amount = order_amount + round(order_amount * 0.10, 2)`.

Исправить цену позиции можно вместе с суммой заказа в одной транзакции. Сумма в представлении оплат сразу изменится вслед за итогом заказа. Отдельная история фактически списанных сумм не предусмотрена заданием.

BR-8.1 требует ровно одну успешную оплату, а BR-8.7 описывает также ожидание и ошибку. В решении заказ, позиции и успешная оплата создаются одной транзакцией. Статусы `ожидает` и `ошибка` допустимы до COMMIT; после фиксации заказ должен быть оплачен. Вторую успешную попытку запрещает частичный UNIQUE, наличие первой проверяет отложенный триггер.

`complete_order`, `complete_positions` и `complete_payments` установлены на `order_core`, `order_structure` и `payment_core`. Они вызывают `order_integrity` в конце транзакции. Проверяются наличие позиции, сумма блюд, единственная успешная оплата и статус заказа (BR-7.10/7.14, BR-8.1/8.7). Удаление последней позиции или успешной оплаты при сохранённом заказе отклоняется. При переносе позиции или платежа проверяются оба заказа; уже удалённый заказ пропускается.

Статус оплаты пересчитывает `sync_payment_status` после INSERT, UPDATE и DELETE. Если есть успех, заказ оплачен. Если все попытки закончились ошибкой, устанавливается ошибка; иначе сохраняется ожидание (BR-8.7). Несогласованный статус, записанный напрямую, не проходит проверку на COMMIT.

`guard_order_truncate` запрещает TRUNCATE всех позиций или оплат, если в базе остаются заказы. Для полной очистки нужно удалить и сами заказы, как это делает `erase_test_data`. Проверка выполняется после TRUNCATE, когда все перечисленные в команде таблицы уже очищены. Поэтому совместная очистка связанных таблиц разрешена, а отдельная очистка дочерней таблицы отклоняется с `23514`.

## Представления и запись данных

Представление заказа сохраняет имена, порядок и типы полей из задания. Исходные поля поддерживают INSERT/UPDATE/DELETE с RETURNING. Комиссия и итог доступны для чтения; DEFAULT идентификатора, времени и статусов берутся из таблицы ядра.

Представление payment сохраняет столбцы из задания. Запись выполняет `write_payment`. Идентификатор и время имеют DEFAULT, но явный NULL остаётся NULL. Переданный `amount` должен совпадать с итогом заблокированного заказа уже при INSERT/UPDATE, иначе возвращается `23514` (BR-8.4). При переносе платежа нужно передать сумму нового заказа. RETURNING возвращает сохранённые поля и вычисленную сумму.

Перед UPDATE/DELETE адаптер блокирует строку оплаты и сверяет её с прочитанным состоянием. Если строку успела изменить другая транзакция, операция возвращает `40001` и требует повторения транзакции.

Интерфейсы `add_product`, `rating_change`, `get_statistic`, `courier_salary`, `how_much_money`, `insert_test_data`, `erase_test_data` сохранены. Для TRUNCATE, новых FK и прямого ON CONFLICT нужны таблицы ядра; ON CONFLICT через payment не поддерживается. Процедура `CALL erase_test_data()` очищает все реальные таблицы. Установочные скрипты создают новую схему и не выполняют миграцию существующих данных.

## Триггеры и параллельные изменения

| Объект | Причина существования и поведение |
|---|---|
| `check_position_restaurant()` | BEFORE-триггер позиций; читает заказ и блюдо с блокировками, отклоняет разные рестораны по BR-7.3, возвращает NEW |
| `guard_restaurant_change()` | Одна BEFORE-функция для изменения ресторана блюда или заказа; не позволяет обойти BR-7.3 обновлением родительской строки, возвращает NEW |
| `order_integrity()` | Одна общая AFTER constraint-функция для трёх таблиц; проверяет окончательное состояние затронутых заказов на COMMIT, возвращает NULL |
| `guard_order_truncate()` | AFTER TRUNCATE позиций и оплат; запрещает оставлять заказы без дочерних строк |
| `sync_payment_status()` | Одна AFTER statement-функция для INSERT/UPDATE/DELETE оплат; по transition tables пересчитывает статус всех затронутых заказов по BR-8.7 |
| `write_payment()` | INSTEAD OF-триггер совместимого представления; проверяет входную сумму, защищает от потери конкурентных изменений, пишет только исходные факты в payment_core |
| `check_rating_integrity()` | Отложенная проверка фактического AVG после изменений блюд, ресторанов и отзывов; флаг генератора её не отключает |
| `clear_ratings()` | AFTER TRUNCATE отзывов; сбрасывает оба вида рейтингов в NULL |
| `rating_change()` | Обязательная функция FOOD-105; AVG и UPDATE находятся непосредственно в её теле, обрабатываются старый и новый объекты, рейтинг заказа не создаётся |

Функции целостности находятся в `02_integrity.sql`, функции рейтингов находятся в `05_rating.sql`. Объявления триггеров собраны в `09_triggers.sql`, ENUM-типы определены в `00_types.sql`. Триггерные функции не принимают пользовательских аргументов. У каждой функции задан `SET search_path`.

Триггеры проверяют условия, для которых требуется читать другие таблицы. Ошибка `23514` прерывает транзакцию при нарушении ограничения. Стандартные ошибки FK и NOT NULL не перехватываются.

Ресторан позиции должен совпадать с рестораном заказа (BR-7.3). `check_position_restaurant` блокирует заказ и блюдо через `FOR NO KEY UPDATE`. Этот же режим используют проверка заказа и пересчёт рейтингов; он совместим с `KEY SHARE` внешних ключей и не требует повышения блокировки SHARE до UPDATE. `guard_restaurant_change` проверяет изменение ресторана у существующего блюда или заказа.

Внутри одного вызова отложенной проверки заказы блокируются по UUID. Проверки одного заказа и изменения позиций одного блюда выполняются последовательно. Взаимоблокировки нескольких пользовательских операций всё ещё возможны: после `40P01` или `40001` нужно повторить всю транзакцию. Это относится и к конфликту адаптера оплаты на `READ COMMITTED`.

Изменение `product.restaurant_id` или `order.restaurant_id` при `REPEATABLE READ` отклоняется с `0A000`. После ожидания блокировки старый снимок может не содержать чужие позиции, которые уже зафиксированы. Для этой операции используется `READ COMMITTED` либо `SERIALIZABLE`. Во втором случае конкурирующие транзакции также должны использовать SERIALIZABLE.

## Рейтинги

Процедура `add_product` принимает все атрибуты блюда, включая `p_rating`. Для нового блюда допустим только `p_rating = NULL`, поскольку отзывов ещё нет (BR-9.7). Любое другое значение, включая 0 и оценки от 1 до 5, отклоняется с `22023`.

После INSERT, UPDATE и DELETE отзыва рейтинг пересчитывается. При переносе отзыва обновляются старая и новая сущности. У заказа отдельного агрегированного рейтинга нет.

`check_rating_integrity` сравнивает итоговый рейтинг с `round(AVG(review.rating), 2)` на COMMIT. Если отзывов нет, ожидается NULL. Проверки на блюдах, ресторанах и отзывах не дают сохранить произвольный рейтинг при INSERT/UPDATE или оставить прежнее значение после изменения отзывов. Согласованные промежуточные изменения внутри транзакции разрешены. TRUNCATE отзывов сбрасывает рейтинги отдельным триггером.

Флаг `lukovkin_food.generating = on` отключает вычисление среднего в `rating_change`, но сохраняет проверки целостности. В этом режиме выполняется `UPDATE SET rating = rating`: значение остаётся прежним, а версия родительской строки меняется. Конкурирующая транзакция со старым снимком REPEATABLE READ получает `40001`. Среднее для нового пакета рассчитывает сам генератор.

## Генератор и отчёты

`insert_test_data(n)` добавляет данные к уже существующим. Каждый пакет содержит n клиентов, курьеров, ресторанов и категорий, а также 5n адресов, блюд, заказов, отзывов и оплат. Из адресов n используются ресторанами, остальные 4n используются клиентами. Связи указывают на существующие строки, историческая цена позиции записывается вместе с расчётом заказа. Части ФИО и реквизиты заполняются в отдельных столбцах, автор отзыва определяется заказом.

Строки генерируются из кириллицы, их длина выбирается от 1 до размера varchar. Фиксированных названий и префиксов нет. Индексы enum начинаются с 1. Первый курьер пакета активен. При совпадении уникального логина, телефона или адреса строка генерируется заново. Пароль формируется через `md5(random()::text)`.

Генератор использует встроенные функции PostgreSQL. Он не вызывает `add_product`, `courier_salary` и вспомогательные расчётные функции, как требует `samples/all_examples.sql`. На время заполнения он устанавливает `lukovkin_food.generating`, самостоятельно рассчитывает рейтинги и возвращает прежнее значение параметра. FK и проверки целостности остаются включёнными. Параметр не ограничивает права доступа: inspector имеет полный доступ к схеме.

После создания заказов пакетами вставляются позиции, отзывы и оплаты. Такой порядок позволяет немедленным FK отзывов увидеть состав заказа. Связанные массивы разворачиваются через `unnest`. Описание отзыва вычисляется до `array_append`, чтобы подзапрос при добавлении не вызывал копирование растущего массива.

Оплаты вставляются одним пакетом в payment_core. Это позволяет обойти построчный адаптер представления и пересчитать статус заказа после всего пакета. Сумма доступна через `payment.amount`. При 5n заказов и 5n оплат каждому заказу соответствует одна успешная попытка; дополнительные неуспешные попытки проверяются отдельно.

История выплат охватывает текущий и пять предыдущих календарных месяцев. Суммы соответствуют доставленным заказам. Первый коэффициент равен 0.1, последующие зависят от числа доставок прошлого месяца. При повторном расчёте `courier_salary` использует сохранённый `coefficient_used`. Уволенный получает заработанное, а ставка сохраняется на уровне месяца увольнения, в том числе в следующих нулевых выплатах.

Даты используют часовой пояс сервера (BR-11.2). Тип `timestamp` хранит локальное время без смещения. Отчётный месяц определяется по `order_timestamp`; условие `status = 'доставлен'` отбирает доставленные заказы.

`get_statistic` читает заказы в один материализованный CTE. По нему отдельно рассчитываются суммы, количество покупок клиентов и объёмы блюд. `DISTINCT ON` выбирает лидеров после сортировки агрегатов; случайный порядок используется только при равенстве количества. Оконных функций и LATERAL в запросе нет. Ресторан без оборота получает 0 в суммах и NULL в полях лидеров.

`how_much_money` строит последовательность месяцев рекурсивным CTE. Обороты и выплаты агрегируются до соединения, чтобы не размножать суммы. LAG применяется после заполнения пропущенных месяцев. При согласованных выплатах месяц без доставок имеет нулевые суммы. Если за такой месяц отдельно внести выплату, отчёт учтёт расход и покажет отрицательный результат по BR-10.2 и FOOD-108.

Права inspector выдаёт `grants.sql` после создания или восстановления схемы. Архив содержит только схему решения с пустыми таблицами; exts в него не входит.
