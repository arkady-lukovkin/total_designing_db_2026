# Ограничения FoodExpress

Схема `lukovkin_food`, PostgreSQL 15 и новее. Концептуальные сущности сохранены. Таблица `"order"` взята в кавычки, поскольку `order` является ключевым словом (BR-13.1).

## Типы

| Тип | Значения | Правило |
|---|---|---|
| restaurant_status | активен, неактивен | BR-4.3 |
| product_status | доступно, нет_в_наличии, архив | BR-5.5 |
| courier_status | свободен, занят, на_доставке, уволен | BR-6.2 |
| order_status | создан, готовится, в_доставке, доставлен, отменён | BR-7.7 |
| order_pay_status | ожидает, оплачен, ошибка | BR-7.9 |
| payment_status | успех, ошибка, в_обработке | BR-8.2 |
| payment_type | карта, наличные, безнал | BR-8.2 |
| review_entity_type | блюдо, ресторан, заказ | BR-9.1 |

Все идентификаторы, включая тестовый внешний идентификатор финансовой транзакции, имеют тип UUID. Значения по умолчанию для идентификаторов сущностей вызывает `exts.uuid_generate_v4()` (BR-11.1). Схема `exts` не создаётся и не изменяется скриптами решения (BR-13.3).

Названия ограничены `varchar(80..120)`, части ФИО — `varchar(50)`, адресные части — `varchar(12)` и `varchar(100)`. Телефон хранится как 11 цифр без оформления, пароль — 32 шестнадцатеричных символа. Реквизиты ресторана разделены на `inn`, `ogrn`, `settlement_account`; они хранятся как строки, чтобы не терять ведущие нули. Проверяется формат из 10/12, 13/15 и 20 цифр соответственно. Проверка контрольных сумм и действительности реквизитов не реализована: это технический формат по BR-11.6, а не интеграция с реестрами.

Денежные значения имеют два знака после запятой, количество — три. Технические диапазоны выбраны по BR-11.6 и замечанию о чрезмерной разрядности в голосовом разборе (00:25–00:52). Это пределы выбранного хранения, **не объявленные заказчиком бизнес-максимумы**. Они ограничивают отдельное блюдо, заказ или выплату; агрегаты отчётов используют `numeric` без такого ограничения.

| Поля | Тип | Верхняя граница хранения | Обоснование |
|---|---|---|---|
| `product.price`, `order_structure.unit_price` | `numeric(7,2)` | 99 999.99 | Цена одной позиции доставки; исключены миллионные цены одной порции |
| `order_structure.quantity` | `numeric(6,3)` | 999.999 | Дробное количество; до тысячи единиц одного блюда в заказе |
| `order.order_amount`, `order.commission` | `numeric(8,2)` | 999 999.99 | Сумма отдельного заказа до комиссии и сама комиссия |
| `order.total_amount`, `payment.amount` | `numeric(9,2)` | 9 999 999.99 | Запас разряда для 10% комиссии поверх максимальной суммы блюд |
| `courier_pay.amount` | `numeric(9,2)` | 9 999 999.99 | Месячная выплата одному курьеру; не миллиардные значения |
| Рейтинги | `numeric(3,2)` | Ограничены CHECK | Дробная оценка и округлённое среднее |
| Коэффициенты | `numeric(2,1)` | Ограничены CHECK 0.1..0.5 | Точность по BR-6.4/BR-10.2 |

Сумма позиций может превысить диапазон суммы заказа: такой заказ не помещается в выбранный формат и должен быть отклонён. Генератор обязан формировать согласованные значения в этих диапазонах; в будущем расширение объёмов потребует явного изменения типов.

Удаление клиента удаляет его связи `client_address`, но не сами адреса. Удаление ресторана также не удаляет адрес. Ссылки заказов не позволяют удалить использованные справочные строки и потерять историю (BR-3.5). При удалении самого заказа его дочерние позиции, попытки оплаты и отзывы удаляются каскадно. Удаление отдельной позиции с отзывом запрещено составным FK.

Связь автора отзыва с клиентом проходит через `review.order_id → order.client_id → client.client_id`. Физического столбца `review.client_id` нет: он однозначно определяется заказом. Представление `review_with_client` возвращает все поля отзыва и вычисленного через JOIN автора. При записи в `review` клиент повторно не передаётся. Это не механизм аутентификации: приложение обязано разрешать пользователю выбирать только его заказы. База гарантирует, что сохранённый автор отзыва всегда является владельцем связанного заказа; представить отдельно другого автора невозможно. Представление предназначено для чтения.

## Проверки, которым недостаточно CHECK

Позиции проверяются триггером `check_position_restaurant`: ресторан блюда должен совпадать с рестораном заказа (BR-7.3). Дополнительные триггеры проверяют изменение ресторана у уже существующего блюда или заказа. Читаемые строки блокируются на время проверки, чтобы параллельное изменение ресторана не прошло между чтением и записью.

Триггеры `complete_order`, `complete_positions`, `complete_payments` отложены до конца транзакции. Все три используют одну функцию `order_integrity` с полной реализацией проверок; дополнительного `validate_order` нет. Она проверяет наличие позиции, равенство `order_amount = round(SUM(quantity * unit_price), 2)`, ровно одну успешную оплату, сумму каждой попытки и агрегированный статус (BR-7.10/7.14, BR-8.1/8.4/8.7).

При переносе позиции или платежа проверяются старый и новый заказы. Перед агрегацией родительские строки блокируются через `FOR NO KEY UPDATE` в порядке UUID внутри одного срабатывания. Это сериализует конкурирующие проверки одного заказа; взаимоблокировки между несколькими пользовательскими операциями всё ещё возможны и приводят к откату одной транзакции. Уже удалённый заказ пропускается, поскольку его дочерние строки удаляются каскадно. Удаление последней позиции или успешной оплаты при сохранённом заказе не проходит проверку.

`sync_payment_status` рассчитывает статус заказа по всем его попыткам после INSERT, UPDATE и DELETE. Успех имеет приоритет, затем проверяются все ошибки, иначе остаётся ожидание (BR-8.7). Прямая запись несогласованного статуса не проходит итоговую проверку.

Полиморфный отзыв хранит `entity_type` и `entity_id`. Дополнительные `product_id` и `restaurant_id` — вычисляемые проекции, а не отдельные исходные сведения. Только подходящая для типа проекция заполнена; составной FK проверяет купленное блюдо либо ресторан заказа. Для типа `заказ` действует CHECK. Это позволяет проверять полиморфную ссылку штатными FK, без поиска несуществующих объектов приложением.

## Вычисления и нормализация

Справочники вынесены отдельно. Адреса клиентов и позиции заказа представлены связями, а не массивами повторяющихся атрибутов. Атрибуты связи зависят от её полного ключа. Название ресторана не копируется в блюда и заказы, логин клиента не копируется в оплаты.

`courier.fio` заменён на фамилию, имя и необязательное отчество. `restaurant.company_details` заменён на отдельные ИНН, ОГРН/ОГРНИП и расчётный счёт. Это детализация концептуальной модели на логическом уровне, разрешённая `docs/erd.md` и BR-13.2, с учётом замечания о 1НФ ресторанов и курьеров в голосовом (00:00–00:24). Реквизиты относятся к конкретному ресторану-партнёру; уникальность ИНН/счёта не навязывается, поскольку несколько ресторанов могут иметь общие реквизиты. Отдельный учёт юридических лиц и истории реквизитов не вводится; BR-4.5 прямо исключает историю.

Транзитивная зависимость `review_id → order_id → client_id` устранена из хранимых исходных атрибутов отзыва. Автор восстанавливается представлением `review_with_client`. Концептуальная связь с клиентом сохранена через заказ; повторного независимого факта нет. При смене владельца заказа представление показывает нового владельца: отдельную неизменяемую историю авторства ТЗ не задаёт.

Физическая модель сохраняет производные поля, прямо заданные контрактом: рейтинги, суммы комиссии/итога и статус оплаты. Это контролируемая избыточность поверх нормализованных исходных фактов, а не основание объявлять любую физическую таблицу строго свободной от производных зависимостей. Комиссия/итог и проекции полиморфной ссылки вычисляются СУБД; статус и рейтинги поддерживаются триггерами. Независимое хранение автора отзыва, в отличие от этих контрактных агрегатов, не требуется и устранено.

`order_structure.unit_price` — явно записанная цена позиции в момент оформления. Она зависит от полного ключа `(order_id, product_id)`, а не от одного блюда: одинаковое блюдо может иметь разные исторические цены в разных заказах. Значения по умолчанию нет; приложение или генератор передаёт снимок цены явно. Изменение `product.price` не переписывает историю. Исправление цены позиции допускается только с согласованным изменением суммы заказа и оплат в одной транзакции.

`order_amount = round(SUM(quantity * unit_price), 2)` проверяется на COMMIT; округление выполняется после суммирования. `commission = round(order_amount * 0.10, 2)`, `total_amount = order_amount + round(order_amount * 0.10, 2)`. Формула комиссии повторяется в определении итога, поскольку PostgreSQL 15 запрещает ссылаться на другой вычисляемый столбец.

## Транзакционный контракт и допущения

BR-8.1 буквально требует ровно одну успешную попытку оплаты, хотя BR-8.7 описывает также состояния ожидания и ошибки. Выбрана строгая трактовка: заказ, позиции и успешная оплата создаются в одной транзакции. `ожидает` и `ошибка` возможны в промежуточных шагах; сохранённый после COMMIT заказ всегда оплачен. Неоплаченные заказы на уровне завершённых транзакций не разрешены. Это осознанное разрешение разночтения, а не утверждение, что обычный коммерческий сервис обязан работать именно так. Частичный UNIQUE запрещает вторую успешную оплату, отложенная проверка требует первую.

Даты используют часовой пояс сервера (BR-11.2); `timestamp` хранит локальное значение без отдельного смещения. Отчётный месяц для заказов определяется `order_timestamp`; фильтр `status = 'доставлен'` отбирает доставленные заказы. Дата доставки не предшествует созданию и обязательна для доставленного заказа. Для остальных статусов она может быть NULL; строгий обратный запрет не добавляется, поскольку BR-7.12 говорит «до этого может быть пустым».

Комментарий заказа необязателен, включая NULL и пустую строку. Описание блюда, ресторана и текст отзыва остаются обязательными по их отдельным BR. Форматы реквизитов, телефонов, размерности numeric и возможность отсутствия отчества — явно указанные решения логической модели, которые не выдаются за дословные бизнес-ограничения.

Проверка позиций заранее блокирует заказ и блюдо в режиме `FOR NO KEY UPDATE`; отложенная проверка заказа и пересчёт рейтингов используют тот же режим. Это устраняет две воспроизведённые взаимоблокировки при повышении `SHARE` до `UPDATE`, сохраняя совместимость с `KEY SHARE` внешних ключей. Изменения позиций одного блюда сериализуются. Отсутствие любых взаимоблокировок не гарантируется: приложение должно повторять целую транзакцию после `40P01`, а при `SERIALIZABLE` также после `40001`.

Фактическое изменение `product.restaurant_id` или `order.restaurant_id` при `REPEATABLE READ` отклоняется с `0A000`: после ожидания родительской блокировки этот уровень сохраняет снимок, в котором могут отсутствовать уже зафиксированные чужие позиции. Для такой операции используется `READ COMMITTED` либо согласованный режим `SERIALIZABLE` у конкурирующих транзакций. Это ограничение конкретной мутации, а не общий запрет `REPEATABLE READ` в БД.

## Назначение дополнительных функций целостности

| Объект | Причина существования и поведение |
|---|---|
| `check_position_restaurant()` | BEFORE-триггер позиций; читает заказ и блюдо с блокировками, отклоняет разные рестораны по BR-7.3, возвращает NEW |
| `guard_restaurant_change()` | Одна BEFORE-функция для изменения ресторана блюда или заказа; не позволяет обойти BR-7.3 обновлением родительской строки, возвращает NEW |
| `order_integrity()` | Одна общая AFTER constraint-функция для трёх таблиц; проверяет окончательное состояние затронутых заказов на COMMIT, возвращает NULL |
| `sync_payment_status()` | Одна AFTER statement-функция для INSERT/UPDATE/DELETE оплат; по transition tables пересчитывает статус всех затронутых заказов по BR-8.7 |
| `rating_change()` | Обязательная функция FOOD-105; AVG и UPDATE находятся непосредственно в её теле, обрабатываются старый и новый объекты, рейтинг заказа не создаётся |

Служебные функции создаются в `02_integrity.sql`, а обязательный пересчёт рейтинга FOOD-105 — в `05_rating.sql`. Они не принимают пользовательские аргументы и вызываются триггерами. Проверки межтабличных агрегатов нельзя выразить обычным CHECK. Исключения с кодом `23514` означают нарушение ограничения и откатывают транзакцию; это намеренное поведение, а не «обработка без прерывания». Код не перехватывает стандартные FK/NOT NULL ошибки и не скрывает их диагностику. Схема фиксирована через `SET search_path` каждой функции.

Для нового блюда `add_product` принимает все атрибуты, включая `p_rating`. Допускается только `p_rating = NULL`: у нового блюда ещё нет отзывов (BR-9.7). Любой вход, отличный от NULL, включая 0 и числа в диапазоне 1–5, отклоняется с SQLSTATE `22023`; значение не игнорируется молча. Последующие INSERT, UPDATE и DELETE отзывов пересчитывают рейтинг, включая старую и новую сущности при переносе отзыва. Для заказа агрегат не создаётся.

## Генератор и расчёты

`insert_test_data(n)` добавляет новый пакет без удаления прежних строк. На пакет приходится n клиентов, курьеров, ресторанов и категорий; 5n адресов, блюд, заказов, отзывов и оплат. n адресов используются ресторанами, 4n — клиентами. Связи должны указывать на существующие записи, а цена каждой позиции фиксируется в `unit_price` одновременно с расчётом суммы заказа. Реквизиты и части ФИО заполняются в новых отдельных столбцах; автор отзыва выводится через заказ.

Случайные строки формируются из кириллицы, от 1 до размера соответствующего varchar. Нет готового набора названий и префиксов. Индекс enum начинается с 1. Первый новый курьер обязательно активен. Коллизии уникального логина, телефона и адреса приводят к повторной генерации строки. Пароль формируется через `md5(random()::text)`.

Генератор использует встроенные функции PostgreSQL и не вызывает свои `add_product`, `courier_salary` или вспомогательные расчётные функции. Во время генерации локальный параметр `lukovkin_food.generating` отключает только пересчёт агрегатов в `rating_change`; FK и остальные проверки продолжают действовать. Затем рейтинги нового пакета рассчитываются самим генератором, параметр возвращается к прежнему значению. Это выполняет запрет из `samples/all_examples.sql` на расчёт генератора через бизнес-процедуры. Параметр не является механизмом разграничения доступа; inspector по заданию имеет полный доступ к учебной схеме.

Позиции и отзывы накапливаются в массивах; после создания всех заказов вставляются пакеты позиций, отзывов и оплат в этом порядке. Немедленные FK отзывов уже видят заполненный состав заказов. Параллельный `unnest` разворачивает связанные массивы одновременно. Описание отзыва вычисляется отдельно перед `array_append`: подзапрос внутри добавления заставлял PostgreSQL копировать растущий массив. Оплаты вставляются одним пакетом, чтобы не пересчитывать их агрегат отдельно для каждой строки. Ровно 5n оплат на 5n заказов означают одну успешную попытку на каждый сгенерированный заказ. Дополнительные неуспешные попытки проверяются отдельно.

История выплат содержит шесть календарных месяцев, включая текущий, с суммами по фактическим доставкам. Коэффициент месяца определяется доставками предыдущего месяца; первый — 0.1. Для повторного расчёта текущего месяца `courier_salary` использует сохранённый `coefficient_used`, а не уже назначенный коэффициент следующего месяца. Уволенный получает заработанное, но его коэффициент не меняется. Генератор замораживает ставку на значении месяца увольнения и сохраняет её в последующих нулевых строках шестимесячной истории.

В `get_statistic` исходная таблица заказов читается один раз в материализованный CTE. Из него отдельно получаются суммы, количество покупок клиентов и объёмы блюд. Победитель определяется через `DISTINCT ON` после сортировки агрегатов; случайный порядок применяется только при равенстве количества. Оконных функций и LATERAL нет. Отсутствующий оборот ресторана возвращается как 0, отсутствующие лидеры — NULL.

`how_much_money` строит месяцы рекурсивным CTE. Зарплаты и обороты агрегируются раздельно до соединения, чтобы строки заказов не размножали выплаты. LAG применяется после заполнения пропущенных месяцев. При согласованных выплатах месяц без доставок имеет нулевые суммы; если отдельно внести ненулевую выплату в такой месяц, отчёт сохранит реальный расход и покажет отрицательный результат по формуле BR-10.2 и FOOD-108.

Права inspector выдаются скриптом `grants.sql` после создания либо восстановления схемы. Архив содержит только `lukovkin_food`, без тестовых строк и без схемы `exts`.
